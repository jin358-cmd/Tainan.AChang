### 1.4 Owner Intervention 與零額外平台成本方案

Owner 不應把密碼貼到聊天或 GitHub。請透過執行環境的 secret store 提供：

1. `SUPABASE_ACCESS_TOKEN` 與 `SUPABASE_DB_PASSWORD`，或一條可供 `pg_dump` 使用的 Session Pooler connection URI。
2. 一個 `age` 公鑰 recipient 或等效 KMS 公鑰；私鑰不得放在 repo 或和備份同位置。
3. 授權的 off-site 儲存位置與 retention policy。

手動 CLI logical dump 的 Supabase 平台固定費用為 USD 0；只可能產生既有配額內的 egress 與外部物件儲存費。替代方案是升級 Pro（官方 billing 範例列出 USD 25/month plan fee，另依 compute/usage 計價；實際金額須以升級畫面為準），可取得 7 天 daily backups，但仍須處理 Storage objects、外部設定與 restore drill。

### 1.5 已準備的備份／還原程序

取得上述 secrets 後，在受控工作目錄以 PostgreSQL 17 client 建立單一 custom-format consistent snapshot，涵蓋全部必要 schema/data，另匯出 roles 與記錄 Edge/Auth/Realtime 設定；立即產生 SHA-256，再以 Owner 公鑰加密後上傳 off-site。明文 dump 在驗證加密檔可解密後安全銷毀。

隔離 restore 使用乾淨 PostgreSQL 17，先建立必要 roles/extensions，再 `pg_restore --no-owner --no-privileges --exit-on-error`。還原後重新執行本報告 row counts、orphans、FK、indexes、RLS、policies、functions、triggers 與關聯查詢。只有 dump、hash、解密、restore 與比對全部成功，EIPP-11 才能改為 PASS。

PostgreSQL restore 不能代表整個 Supabase project 已復原：API keys、Auth provider settings、Edge Functions/secrets、Realtime settings 與實際 Storage objects 必須另行保存與重建。本專案目前沒有 Storage objects，仍需在 runbook 明確記錄。
